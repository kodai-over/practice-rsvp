# 改善要望のまとめと対応

スタジオ練出欠管理 のメンバーがアプリの「要望」から送った改善要望を、**サマリーを見せる → 次のアクションを提案する → 改善案を出す → 管理者が承認したものだけ実装する → 改善済みにする** の順で扱う。
承認なしに実装・デプロイ・シートの書き換えをしない。

## 要望の置き場所

- スプレッドシート「スタジオ練出欠管理」の **「要望」シート**（アプリの各画面の右下「💬 要望」ボタンから送られるデータ）
- スプレッドシートIDは `apps/gas/.clasp.json` の `parentId`（git には入っていないローカルファイル）
- 列: `要望ID` / `投稿者`（LINEユーザーID） / `投稿者名` / `内容` / `状態` / `管理者コメント` / `投稿日時`
- 状態は `未対応` / `検討中` / `改善済み` / `見送り` のいずれか（`packages/shared/src/types.ts` の `FEEDBACK_STATUSES`）
- 要望は送るだけで、一覧と管理者コメントをアプリで見られるのは管理者だけ（一般メンバーには見えない）。それでも文面は丁寧に、個人を責める内容は書かない

## 手順

### 1. 要望を集める
1. `apps/gas/.clasp.json` を読んでスプレッドシートIDを得る
2. Google Sheets のツール（`get_values`）で `要望!A1:G` を読む。ツールが使えなければ、ユーザーにシートの内容を貼ってもらう
3. 状態が `未対応` と `検討中` のものを対象にする（`改善済み`・`見送り` は参考として件数だけ数える）

### 2. 要望のサマリーを見せる（改善案より先に）
改善案を考える前に、**どんな声が届いているか** を管理者に見せる。この時点ではまだ実装案を出さない。

1. **全体の数字**（1行）: 全件数、状態ごとの件数（未対応 / 検討中 / 改善済み / 見送り）、投稿した人数、いちばん新しい投稿日
2. **届いている声**: 同じ趣旨の要望を1つのテーマにまとめ、テーマごとに次の表で示す。件数の多い順、同数なら新しい順にする

   | テーマ | 種類 | 件数（投稿者数） | 届いている声（要約） | 投稿者名 | 最新の投稿日 |
   | --- | --- | --- | --- | --- | --- |

   - 種類: 不具合 / 使い勝手の改善 / 新機能 / 質問・その他
   - 「届いている声」は原文を短く言い換える。1つのテーマに複数あれば代表的なものを2〜3個まで
   - 同じ人が同じ内容を何度も送っていれば、件数とは別に注記する
3. **気づいたこと**（箇条書き2〜3個まで）: 例として、複数の人が同じ所でつまずいている、最近のリリース後に増えた、すでにできるのに知られていない（コードと仕様を見て判断する）、など
4. 対象（未対応・検討中）が0件なら、そう伝えて終える

### 3. 次のアクションを提案する（ここで一度止まる）
テーマごとに、次のどれを勧めるかを1行で示す。そのあと AskUserQuestion（複数選択）で、どのテーマを先に進めるかを管理者に選んでもらう。

| アクション | 使う場面 |
| --- | --- |
| 改善案を作る | 直す価値があり、何を変えるか決めたい |
| 案内で解決 | すでにできる、または設定で解決できる。案内文（管理者コメント）の案を添える |
| 詳しく聞く | 内容があいまいで、何に困っているか分からない。投稿者に聞く質問の案を添える |
| 見送り | 制約に反する、効果より負担が大きい。理由の案を添える |
| 様子を見る | 1件だけで判断しにくい。同じ声が増えたら改めて検討する |

選ばれたテーマだけ次の手順に進む。「案内で解決」「見送り」は手順6の文面確認へ、「詳しく聞く」は質問文を管理者に渡して終える。

### 4. 改善案を出す（ここで一度止まる）
「改善案を作る」が選ばれたテーマについて、コードと仕様を確認して案を出す。次の制約に反する案は出さないか、反する点を明記する。

- LINE公式アカウントの無料プランは月200通。グループへのプッシュ通知を増やす案は通数の見積もりを付ける
- Gemini API は無料枠（請求先アカウントにつながない）
- 操作は「スクショを送ってボタンを押すだけ」「ボタン1回」を最優先にする

テーマごとに次の表で示す。

| # | 対象の要望（要望ID・投稿者名） | 要望の要約 | 改善案 | 変更する場所 | 規模（小/中/大） | 注意点（通知数・費用など） |
| --- | --- | --- | --- | --- | --- | --- |

そのあと AskUserQuestion（複数選択）で **どの案を実装するか** を管理者に選んでもらう。見送る案があれば理由も確認する。
承認が出るまで実装しない。

### 5. 承認された案を実装する
- 承認された要望の状態を、着手時に `検討中` にしてよいか確認してから更新する
- このリポジトリの作法に従う
  - 業務ロジックは `apps/gas/src/app/`（GAS非依存）に書き、`apps/gas/test/` にテストを足す
  - 画面は `apps/liff/src/`。`npm run dev:mock -w @studio-attendance/liff` で、スマホ幅で確認する
  - 共通の型・ルールは `packages/shared/src/`
- `npm test` と `npm run typecheck`、`npm run build -w @studio-attendance/gas`、`npm run build -w @studio-attendance/liff` が通ることを確かめる
- コミットは git-workflow スキルの規約に従う
- **デプロイ（`npm run deploy -w @studio-attendance/gas` と `git push`）は管理者の了解を得てから行う**

### 6. 改善済みにする
実装（とデプロイ）が終わったら、対応した要望ごとに次を書く文面を管理者に見せ、了解を得てからシートを更新する（`update_values`）。

- `状態`: `改善済み`
- `管理者コメント`: `改善済み（YYYY-MM-DD）: <何をどう変えたか。利用者向けの言葉で1〜2文>`
  - 例: `改善済み（2026-11-02）: 練習の前日に、アプリの「自分が行く」タブに印が付くようにしました。`

見送った要望は、管理者が了解した場合だけ `状態: 見送り`・`管理者コメント: 見送り（YYYY-MM-DD）: <理由>` にする。
「案内で解決」とした要望は、管理者が了解した場合だけ `状態: 改善済み`・`管理者コメント: ご案内（YYYY-MM-DD）: <すでにできるやり方>` にする。
「詳しく聞く」「様子を見る」とした要望は状態を変えない（管理者が望めば `検討中` にする）。

### 7. 報告する
- 対応した要望（要望ID・テーマ・変えたこと）
- 案内で解決した要望と案内した内容
- 見送った要望と理由
- 投稿者に詳しく聞くことにした要望と、聞く質問
- 未対応のまま残した要望
- デプロイしたかどうか（していなければその旨）
